# Codex · R2-live：训练 / 导出 / sweep 调度

本轮仅提交想法，不改代码、不重训、不跑实验。以 HOST 锁定测量为准；下述收益为条件估算，不是新增实测。历史 handler_init、#43 bare-read 属于不同计时口径，不直接相加或互换。

## 卡 1：按依赖分组，一次初始化服务多臂；禁止跨窗硬共享

- **本仓锚点**：[sweep_live_adapter.py](/workspace/MyQuant/my_scripts/sweep_live_adapter.py:114) 的 `_predict_once()` 已在单进程缓存 pred/label；`set_segments()` 切窗会清缓存。[sweep_ranking.py](/workspace/MyQuant/my_scripts/sweep_ranking.py:214) 已串行执行网格。因此，“同窗排名网格一次 init”是已有能力。
- **提案（调度级）**：把共享范围显式分成三层：
  1. handler 组：数据版本、宇宙、特征、gate、窗口、processor 及其拟合窗口全部相同；
  2. 模型组：handler 组内，按模型参数、随机种子分组；
  3. 下游臂：模型与预测相同，仅名单参数或导出配置不同。
  
  每次只驻留一个 handler 组，组内模型与下游臂串行完成后释放。先覆盖既有排名 sweep，再考虑模型参数 sweep。
- **收益**：现有同进程排名网格不再记新增收益。对目前拆成多个启动、但确实兼容的任务，理论可省 `(组内任务数−1) × 初始化成本`，扣除调度开销；model_fit 约 5.6s，不值得优先并行化。
- **成本与风险**：共享 dataset 可能被模型或 processor 原地修改；Windows 子进程会重新 Loading 或复制大对象。组键设计和状态隔离比循环调度更难。
- **冻结检查**：topk、过滤默认、训练/验证/测试窗及 learn/infer 分工不变。改 gate 或窗口必须 MISS、另建组；不得把多窗并成大窗重新拟合归一化器。
- **对抗预填**：“现有代码已经一次 init，这不是重复提案吗？”——是，所以只计算**跨启动合批与新增兼容模型臂**的增量；若实际任务本来全在一进程，收益为零。
- **建议裁决**：**裁剪后采纳**——先做明确分组和串行生命周期，不引入进程池。
- **重提条件**：出现反复启动的同配置任务，或模型参数 sweep 明确需要共享 handler；扩到多模型前须证明共享对象不会被污染。

## 卡 2：预测产物成为续跑入口，失败后只补下游

- **本仓锚点**：[custom_train_backtest.py](/workspace/MyQuant/my_scripts/custom_train_backtest.py:495) 已由 `SignalRecord` 生成预测产物；[export_daily_pool.py](/workspace/MyQuant/my_scripts/export_daily_pool.py:249) 已从预测文件独立导出；adapter 当前仅进程内缓存，返回的 `pred_path` 为空。
- **提案（缓存级 / 调度级）**：在预测完成后保存可校验的 pred/label 与来源记录，供后续 sweep 重启使用；导出只依赖 pred。仅保存下游所需的窄表，不从 handler `fetch()` 巨型特征表再转 parquet。
  
  复用键覆盖数据快照、完整 gate/窗口/processor 配置、模型参数与种子、相关代码及依赖版本；产物另记内容 digest。先完成写入与校验，再发布完成标记。恢复日志明确写 HIT/MISS 及原因。
- **收益**：下游导出或网格中途失败后，可避免重付 handler_init、fit、predict；首次运行没有这部分收益，还增加一次产物写入。已有独立导出路径不重复计功。
- **成本与风险**：磁盘空间、序列化和哈希耗时；只认文件名会误复用，只有 pred 而 label 缺失也不能恢复评分。Windows 文件占用可能阻止替换，失败必须保留为未完成状态。
- **冻结检查**：数据原地修订、改 gate、改任一窗口必须 MISS；预测及标签索引、缺失值口径不变。下游配置另记 digest，不能因预测 HIT 就跳过配置不同的名单计算。
- **对抗预填**：“#43 handler-cache 已经解决了，为什么还要一层？”——handler-cache 服务特征与训练；预测产物服务已经完成训练的下游。仅在重复下游或恢复场景下成立，不默认叠加两套全量缓存。
- **建议裁决**：**裁剪后采纳**——先接通已有预测产物与 sweep 续跑，暂不建设通用缓存平台。
- **重提条件**：出现一次可复现的下游失败重付 Loading，或同一预测被多次导出/评分；以节省墙钟超过产物读写及校验成本为验收门槛。

## 卡 3：把共享耗时记到父任务，停止“零秒 sweep”和重复摊账

- **本仓锚点**：[sweep_ranking.py](/workspace/MyQuant/my_scripts/sweep_ranking.py:149) 支持 payload timings，但缺失时填入 `total_seconds: 0`；adapter 当前未提供 timings。训练入口已有 handler_init、model_fit、SignalRecord 等节点。
- **提案（纪律级 / 调度级）**：新增一次批次的父记录，记录：
  `preflight → handler查键/读取或构建 → fit → predict → 产物提交 → 各臂计算 → 汇总`。
  
  父记录承担共享成本，各臂只记独占耗时并引用父 ID。缺失计时标为未知，不能当零；另记端到端墙钟、缓存状态、失败阶段与已完成臂。配套逐臂完成记录，重启时经 digest 校验跳过已完成臂。
- **收益**：计时本身不承诺加速；收益来自识别隐藏 Loading，以及失败后少跑已完成任务。避免把一次 init 重复算进每臂，或用零秒 manifest 虚报提速。
- **成本与风险**：需维护 manifest 兼容性；每臂频繁写盘可能增加 Windows 小文件开销。完成标记若早于结果持久化，会错误跳过任务。
- **冻结检查**：保留启动时 git 溯源；缓存读取耗时照计。父任务墙钟独立测量，不能简单相加嵌套节点；失败任务不能伪装为完成。
- **对抗预填**：“每臂平均耗时下降，是不是只是摊薄 init？”——报告必须同时列冷启动整批、HIT 整批、单臂独占耗时及配置数；摊销收益与实际计算提速分开。
- **建议裁决**：**采纳**。
- **重提条件**：后续要求更细节点时，先证明当前粒度无法定位瓶颈；若记录 IO 成为热点，再考虑批量写入，不先引入重型追踪服务。

## 卡 4：预测按日组织一次，sweep 与导出减少重复扫描和排序

- **本仓锚点**：[sweep_live_adapter.py](/workspace/MyQuant/my_scripts/sweep_live_adapter.py:183) 的 `_simulate_list()` 每臂每天重复 `xs()`、排序及构建排名字典；[export_daily_pool.py](/workspace/MyQuant/my_scripts/export_daily_pool.py:192) 每天对全预测表做日期布尔筛选再排序。
- **提案（调度级 / IO级）**：在同一预测产物下，sweep 预先生成按日分组、排序结果和排名映射，各臂保有独立持仓状态；导出先按日分组，避免每日扫描整表。第一版只做进程内复用，不新增磁盘缓存。
  
  sweep 与导出分别保留当前排序规则；中性化配置不同的导出不能共享中性化后的排名。
- **收益**：砍的是 init 之后的重复扫描、排序与索引构造。若有 G 臂，每日排序可由 G 次降到一次；持仓演算仍需逐臂执行。导出的日期筛选可由约 D 次全表扫描变为一次分组。整轮能省几分钟须实测，不能套用初始化收益。
- **成本与风险**：预建字典可能增加内存；排序并列、重复代码和非法代码处理稍有变化就会改变名单。大表应避免同时保留多份 DataFrame 副本。
- **冻结检查**：导出保持 score 降序、instrument 升序、去重和非法代码计数；保持 `pred_minus_one` 使用下一预测日期、末日不导出、LF 无 BOM。sweep 保持现有并列顺序、持仓年龄和标签口径。
- **对抗预填**：“顺便用 `nlargest(topk)` 更快？”——不纳入本卡；持仓淘汰可能依赖完整排名，导出前截断也可能改变去重后的名单。
- **建议裁决**：**裁剪后采纳**——先消除重复分组与排序，暂不改截断算法。
- **重提条件**：若节点计时显示下游耗时可忽略，则降为远期；只有网格规模扩大且额外内存可控，才考虑更复杂预计算。

## 合批验收建议

后续获准实施时，将涉及 handler_init 的改动放进同一批 Windows 验收：一次冷启动、多臂共享、同配置重启 HIT、改 gate MISS、改窗 MISS、下游失败恢复。MISS 验证可先检查键与调度决策，避免每个反例都完整初始化。

Linux 用小型固定输入验证分组、恢复及名单等价；真实 Loading、文件替换和峰值内存留给 Windows。**不以加速为理由调整 topk、过滤默认或正确性 gate，也不把盲目提高 kernels 列入调度方案。**
